Web Package Tools Administrator Manual

Internal operating manual for building offline course packages, managing the course catalog, generating machine-bound licenses, supporting distributors, and recovering license-generation capability.
Revision: August 2026 · Based on the supplied Web Package Tools source package

Purpose and roles

Web Package Tools turns static HTML5 course modules into portable Windows EXE packages and, when enabled, protects those packages with an offline course license. The internal tools are intended only for authorized employees who build packages or manage distributor relationships.

RoleUsesDoes not receive
Package administratorWeb Package Builder, Batch Builder, course catalog, protected-package creationNothing beyond normal internal access
License operatorWeb Package License Generator, signing-key recovery, course catalog, installed-license troubleshootingSource code is not required
DistributorCompiled course EXE modules and, when activation is required, the machine-specific .wpl license supplied by the course administratorBuilder, License Generator, signing key, course catalog, source code
Keep the signing authority internal. The .wpkey recovery backup represents the authority to create valid licenses. It is appropriate for designated internal primary and backup operators, but it must not be sent to a distributor.

A single machine license applies to one Salesforce Product Code. Every licensed module packaged with that same Product Code uses the same installed course license on that computer.

Install and first run

The internal deployment package is Web Package Tools. The MSI installs the Web Package Builder and Web Package License Generator into the same application directory so the generator can load the shared WebPackageViewer assembly.

  1. Run WebPackageTools.msi on the authorized employee's Windows computer.
  2. Launch Web Package Builder and Web Package License Generator from the Start menu to verify both applications start.
  3. For a new operator computer, open Operator Setup in the License Generator, restore the existing .wpkey, and import the current .wpcourses catalog.
  4. Confirm the signing status says the installed identity matches the current WebPackageViewer build.
Normal operators do not need PowerShell, Git, Visual Studio, ILRepack, or the source repository. Those are development concerns only.

Build one module

Web Package Builder — rendered from the current WPF layout.
  1. Open Web Package Builder.
  2. For Web Site Folder, choose the module's index.html. The builder stores its containing folder.
  3. Review the automatically detected values. The builder reads the HTML <title>, detects the iSpring size comment when present, suggests the module ID from titles such as “Module 0,” and suggests an output filename beside the source folder.
  4. Use Initial URL and Virtual Path only when the package requires something other than the normal /index.html and / values.
  5. For a production licensed course, check Require offline license, choose the canonical course, and verify the Module ID and Module Name.
  6. Choose or confirm the output EXE and click Build Package. If the file already exists, the builder asks before replacing it.
Licensed build: the package uses the protected payload format and validates the machine/course license before decrypting the embedded website.
Unlicensed build: leave Require offline license unchecked. This preserves the original WebPackageViewer package behavior and does not require a .wpl.

Batch build a course

Batch Package Builder — rendered from the current WPF layout.

Batch Build is intended for courses that contain many separately published HTML5 module folders.

  1. From the normal Builder, click Batch Build....
  2. Select the canonical course and choose an output folder.
  3. Click Add Course Folder... and select the parent directory. The builder recursively discovers every folder containing an index.html.
  4. Review the grid. Module ID, Module Name, and Output File are editable. Source Folder and Window Title are informational.
  5. Correct any module whose title does not produce a Module ID automatically. Titles matching “Module N” are normalized to IDs such as M00, M01, and M12.
  6. Leave Require offline license (protected payload) checked for production licensed packages and click Build All.

The builder rejects duplicate output filenames and stops if a row is missing required metadata. Use Remove Selected to exclude specific discovered modules or Clear to start over.

Course and module metadata

Salesforce Product Code

This is the stable license identity. One installed .wpl unlocks every module whose package uses that Product Code. Do not change the Product Code merely because a course name or version changes.

Course Name and Version

These are descriptive. They can be edited without changing the stable license identity. Course Version is not currently part of the authorization check.

Module ID and Module Name

These identify the individual packaged module but do not create separate course licenses. The module name defaults to the HTML/window title unless an operator edits it.

Generate a course license

Web Package License Generator — current application screenshot.
  1. Open Web Package License Generator. Verify the Signing Key status says the installed signing identity matches the WebPackageViewer build.
  2. Select the course. Verify the Salesforce Product Code and Course Name.
  3. Enter the distributor/customer identifier used by your internal process.
  4. Paste the Machine ID copied from the distributor's activation screen. Dashes and spaces are normalized; the final ID must contain 32 hexadecimal characters.
  5. Choose whether the license never expires. If not, select an expiration date.
  6. Click Generate License... and save the .wpl.
  7. Return the .wpl to the intended computer for import through its activation screen.
Generating a license file does not install or replace a license already active on the operator's own computer. Use Installed Licenses... to inspect the license actually being used locally.

The generated file is valid only when all of the following match: the signature, the Salesforce Product Code, the target Machine ID, and—when present—the expiration date.

Expiration dates

License never expires is checked by default. When it is unchecked, the selected date is encoded as the end of that day based on the issuing computer's local time and stored in UTC.

Test carefully: when verifying expiration, make sure the test date is actually in the past including the year. The Installed Licenses window displays the expiration date of the license currently installed on the local machine.

When an expired license is presented or already installed, the course reports This offline license has expired. Generate a replacement .wpl for the same Product Code and Machine ID to renew access.

Installed license troubleshooting

Installed Course Licenses — current application screenshot showing active and disabled licenses.

This window is for support and local testing. It scans both ProgramData and LocalAppData license locations.

ActionUse
Disable LicenseTemporarily renames the selected active .wpl so the course behaves as unactivated. This is the preferred troubleshooting action.
Enable LicenseMakes a disabled license active again.
Delete LicensePermanently deletes the selected local license file. The computer will require activation again.
RefreshReloads the list from both storage locations.
Important: enabling a disabled license replaces any currently active license file for the same course path. If an active and disabled copy both exist, select deliberately.

Recommended support test

  1. Select the active course license and click Disable License.
  2. Launch a fresh course EXE. The activation window should appear.
  3. Test the intended .wpl.
  4. Return to Installed Licenses and either keep the newly imported license or re-enable the previous disabled license.

Signing-key backup and recovery

Signing Key Recovery — rendered from the current WPF layout.

The normal private signing key is protected for the current Windows user and is not portable by itself. Use Export Recovery Backup... to create the portable .wpkey.

  1. Click Export Recovery Backup....
  2. Enter and confirm a recovery password of at least 12 characters.
  3. Save the .wpkey to a secure company-controlled location.
  4. Store the password separately from the backup file.
Do not lose the signing identity and do not replace it casually. Existing course EXEs contain the matching public verification key. A newly generated unrelated signing identity would produce licenses that those existing packages reject.

Restore Recovery Backup... can reinstall the same identity for another authorized Windows user/computer. If a key is already present, the application warns before continuing.

Provision another authorized license operator

License Operator Setup — rendered from the current WPF layout.

Use this screen for the designated primary operator, backup operator, or replacement laptop.

  1. Install the same current Web Package Tools MSI.
  2. Open Operator Setup....
  3. Click Restore Signing Key... and restore the existing company .wpkey.
  4. Click Import Course Catalog... and import the current .wpcourses. Import replaces the local catalog.
  5. Confirm the screen reports Signing identity: Ready and shows the expected course count.
  6. As an acceptance test, generate a license on the new operator computer and verify an older already-built protected course EXE accepts it.

The primary and backup operators should use the same signing identity, not separate RSA identities.

Distributor support workflow

  1. Distributor launches a licensed course EXE and receives the Offline License Required window.
  2. Distributor clicks Copy and sends the Course ID and Machine ID to the authorized internal contact.
  3. Internal operator selects the matching course, enters the distributor/customer identifier and Machine ID, chooses expiration policy, and generates the .wpl.
  4. Distributor imports the returned .wpl.
  5. The same license unlocks every module packaged with the same Salesforce Product Code on that computer.

New computer = new Machine ID. A license created for one computer is intentionally rejected on another computer.

Security model and boundaries

The system is designed to discourage casual sharing while remaining fully offline. Licensed packages are machine-bound, course-bound, signed, and use a protected payload. Authorization is checked before the embedded website is decrypted.

  • A copied course EXE can start on another computer, but it cannot open protected content without a license generated for that machine and Product Code.
  • A copied .wpl is rejected on a different computer or different course.
  • Modified protected package data is rejected by the integrity check.
  • The system does not depend on an online license server.
This is not high-assurance anti-reverse-engineering DRM. After successful authorization, the website is temporarily materialized for WebView2 while the course is running. A sufficiently technical authorized user could inspect runtime files, and a determined reverse engineer could analyze the application. The intended threat model is casual redistribution, not a determined software-analysis adversary.

MSI and release workflow

The internal MSI is for employees who build packages or generate licenses. Course modules remain standalone EXEs; distributors do not install the internal tool MSI.

Developer release

  1. Open the solution in Visual Studio and select Release.
  2. Build/Rebuild the solution. The WebPackageViewer project automatically invokes its post-build process, including ILRepack, through MSBuild.
  3. The Setup project packages the final root-level WebPackageViewer.exe and the License Generator primary output into WebPackageTools.msi.
  4. Install the MSI on a test machine or uninstall/reinstall the prior test build, then run both Start-menu applications.
The MSI must not contain the private .wpkey, PrivateKey.protected, issued .wpl files, or other operator-specific secrets.

Developer-only appendix

Graphical builder command

The unpackaged viewer can explicitly open the builder with WebPackageViewer.exe builder. Double-clicking an unpackaged viewer with no obvious site also opens the GUI builder.

Legacy CLI

WebPackageViewer.exe package --output Packaged.exe --zipfolder WebSite
WebPackageViewer.exe unpackage --package Packaged.exe --output OutputFolder
WebPackageViewer.exe "C:\WebSite"
Do not use the legacy CLI package command for production licensed packages. The GUI builder is the path that writes course metadata and selects the protected licensed payload format.

Signing-key initialization

Tools\Initialize-OfflineLicenseKeys.ps1 is a bootstrap/developer operation for establishing a brand-new signing identity. Once production packages and licenses exist, do not regenerate the identity. Migrate the existing identity with the .wpkey recovery workflow instead.

Protected package compatibility

Legacy unlicensed packages continue to use the original WebPackageViewer format. Licensed GUI builds use the protected format. This allows existing nonlicensed packages to remain compatible while production licensed packages receive the additional authorization and integrity layer.
